# Test Aurora Global Database headless secondary DR with AWS FIS

Sample code accompanying the AWS Database Blog post **"Test Aurora Global
Database headless secondary DR with AWS FIS"** (DBBLOG-5791). This repository
demonstrates the setup used in the post; it is sample code tied to the blog and
is not a supported product or library.

The two AWS CloudFormation templates provision the *setup* for the walkthrough.
The *operational* steps in the post — injecting the fault, promoting the
secondary, validating data, and cleanup — remain AWS CLI commands you run
against the deployed resources, because they are actions rather than
infrastructure.

## What the templates create

| Template | Region | Creates |
|---|---|---|
| `cloudformation/01-primary-region.yaml` | us-east-1 | Isolated VPC (10.42.0.0/16), 3 private subnets, SSM interface endpoints + S3 gateway endpoint, SSM-managed access instance, Aurora **global** cluster, **primary** regional cluster + writer (`db.r6g.large`), and the AWS FIS role + `disrupt-connectivity` experiment template |
| `cloudformation/02-secondary-region.yaml` | ap-south-1 | Isolated VPC (10.43.0.0/16), 3 private subnets, SSM endpoints, SSM-managed validation instance, and the **headless secondary** cluster (no DB instance) attached to the global cluster |

A global database spans two Regions, and a CloudFormation stack is single-Region,
so the setup is split into two stacks that you deploy in order.

## Prerequisites

- An AWS account with permissions to create Amazon VPC, Aurora, AWS FIS, IAM,
  Amazon EC2, and Systems Manager resources in two Regions.
- AWS CLI v2.
- The Session Manager plugin on your workstation (to connect to the access
  instances).
- Aurora Global Database requires memory-optimized (R-family) instance classes;
  the smallest supported is `db.r6g.large`.

## Deploy (setup — Steps 1–4 in the post)

Deploy the primary Region first, wait for it to complete, then the secondary.

```bash
# 1) Primary Region (us-east-1) - PostgreSQL defaults
aws cloudformation deploy \
  --region us-east-1 \
  --stack-name dbblog-5791-primary \
  --template-file cloudformation/01-primary-region.yaml \
  --capabilities CAPABILITY_NAMED_IAM

# 2) Secondary Region (ap-south-1) - after the primary stack is CREATE_COMPLETE
aws cloudformation deploy \
  --region ap-south-1 \
  --stack-name dbblog-5791-secondary \
  --template-file cloudformation/02-secondary-region.yaml \
  --capabilities CAPABILITY_NAMED_IAM
```

The same two templates deploy either engine — pass the matching parameter
file. Ready-to-run parameter files are in `cloudformation/parameters/`:

```bash
# PostgreSQL (default) — pass parameters/postgresql.json to both stacks
aws cloudformation deploy --region us-east-1 \
  --stack-name dbblog-5791-primary \
  --template-file cloudformation/01-primary-region.yaml \
  --parameter-overrides file://cloudformation/parameters/postgresql.json \
  --capabilities CAPABILITY_NAMED_IAM

# Aurora MySQL — pass parameters/mysql.json to both stacks instead
aws cloudformation deploy --region us-east-1 \
  --stack-name dbblog-5791-primary \
  --template-file cloudformation/01-primary-region.yaml \
  --parameter-overrides file://cloudformation/parameters/mysql.json \
  --capabilities CAPABILITY_NAMED_IAM
```

Use the same engine and version for both the primary and secondary stacks — a
global database cannot mix engines. Check a supported version with
`aws rds describe-db-engine-versions --engine aurora-postgresql` (or
`--engine aurora-mysql`). Aurora MySQL global databases in ap-south-1 require
version 3.01.0 or higher.

## Useful stack outputs

From the primary stack:

- `PrimaryClusterEndpoint` — writer endpoint to connect to (Step 3).
- `MasterUserSecretArn` — Secrets Manager ARN with the cluster admin credentials
  (generated by the stack; RDS-managed passwords are not supported for Aurora
  global databases).
- `SeedInstanceId` — connect with `aws ssm start-session --target <id>` to seed data.
- `FisExperimentTemplateId` — pass to `aws fis start-experiment` (Step 5).

From the secondary stack:

- `SecondaryClusterArn` — pass to `aws rds failover-global-cluster` (Step 6).
- `ValidateInstanceId` — connect to validate data after failover (Step 6).

## Operational steps (run from the post)

These stay as CLI because they are actions, not infrastructure:

1. **Seed + baseline (Step 3):** connect through the seed instance, create the
   `dr_test` table, insert the 5 rows, and capture the row-count + MD5 checksum.
2. **Inject the fault (Step 5):**
   `aws fis start-experiment --experiment-template-id <FisExperimentTemplateId>`.
3. **Fail over (Step 6):** add a `db.r6g.large` instance to the secondary, then
   `aws rds failover-global-cluster ... --allow-data-loss`.
4. **Validate (Step 6):** re-run the checksum on the promoted secondary and
   confirm it matches the baseline.

## Clean up

Delete the DB instance you added to the secondary during failover and detach any
promoted cluster from the global cluster, then delete the stacks (secondary
first, then primary):

```bash
aws rds delete-db-instance --region ap-south-1 \
  --db-instance-identifier dbblog-5791-secondary-instance-1 --skip-final-snapshot

aws cloudformation delete-stack --region ap-south-1 --stack-name dbblog-5791-secondary
aws cloudformation delete-stack --region us-east-1  --stack-name dbblog-5791-primary
```

If `delete-global-cluster` blocks because members remain, run
`aws rds remove-from-global-cluster` for each regional cluster first.

## Notes

- The `disrupt-connectivity` action applies a deny-all NACL to the primary
  subnets. It blocks the network path only; it does not stop Aurora
  storage-layer replication or the Global Database control plane.
- The VPCs are isolated (no internet gateway or NAT). The access instances reach
  Systems Manager through the interface endpoints, and reach the Amazon Linux
  package repositories through the S3 gateway endpoint.
